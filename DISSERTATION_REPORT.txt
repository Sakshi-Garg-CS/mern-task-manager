================================================================================
                               ABSTRACT
================================================================================

In small offices and college project groups, work is often planned on phone
calls or shared Excel files. After a few days it becomes hard to remember who
is working on what, and whether the job is still pending or already done.
That was the practical problem I wanted to solve.

I built a browser-based Task Management System using MongoDB, Express, React,
and Node.js. There are two login types. The admin creates tasks, picks team
members, watches charts on the dashboard, and can download Excel sheets.
Normal members log in and see only tasks assigned to them. They update work
by ticking checklist items, and the status moves to In Progress or Completed
without the admin changing it manually each time.

Login is protected using JWT tokens and passwords are stored using bcrypt.
I tested registration, task creation, assignment, checklist update, and
report download on my own machine and on MongoDB Atlas. The final version
runs stable for a small team size and is suitable as a demonstration
prototype.

Keywords: MERN, Task Management, React, REST API, MongoDB, JWT, RBAC

          CHAPTER 1 – INTRODUCTION AND OBJECTIVES
================================================================================

1.1  Overview of the Project

In small teams, work is often tracked on WhatsApp or Excel. When one person
finishes a task but does not update the sheet, others still see it as pending.
This causes delay and repeated status checking by the team lead.

This project builds a Web-Based Task Management System using the MERN stack.
After login, an admin creates tasks, assigns members, views dashboard charts,
and downloads Excel reports. A member sees only assigned tasks and updates
progress through a checklist; status changes automatically to Pending, In
Progress, or Completed.

Tools like Jira, ClickUp, and Trello already offer similar services, but they
are commercial products whose source and database are not open for academic
study. This dissertation develops a smaller custom system so that UI, REST API,
JWT security, and MongoDB design can be explained in the viva. It is meant for
small teams (about 5–50 users) as a learning prototype, not as a replacement
for industry platforms.

1.2  Problem Definition

First, there is no shared board showing task name, priority, due date, and
current status in one place. Second, the team lead cannot quickly see how many
tasks are pending versus completed. Third, workers have no simple method to
show progress except sending messages. Fourth, management sometimes needs a
downloadable list for meetings, which a chat group cannot provide.

1.3  Aim

The aim is to plan, code, and test a task management web application where
admin and member roles behave differently but use the same database.

1.4  Objectives

1. Collect requirements for admin and member screens.
2. Design User and Task collections in MongoDB.
3. Write REST APIs for authentication, tasks, and reports.
4. Create React pages for dashboard, task cards, forms, and member views.
5. Link checklist ticks to automatic status change on the server.
6. Perform manual unit, integration, and system testing and document results.

1.5  Scope

The project targets small teams (about 5–50 users). Mobile apps, payment
modules, Gantt scheduling, and email alerts are out of scope. Testing was done
on Windows laptop using Chrome browser.

1.6  Organisation of Report

Chapter 2 lists tools and environment. Chapter 3 is the analysis document.
Chapter 4 is design. Chapter 5 is implementation overview. Chapter 6 contains
program code with comments. Chapter 7 is testing. Chapter 8 shows input and
output screens. Chapters 9 and 10 discuss limitations and future scope.

Teams often use Excel or WhatsApp. Excel lacks real-time role control;
WhatsApp lacks structured task fields and reports. Commercial tools (Trello,

3.5  Data Flow Diagram (DFD)

Level 0 (Context Diagram):
  [Admin] ----> [Task Management System] ----> [MongoDB Database]
  [Member] ---> [Task Management System] ----> [MongoDB Database]

Level 1 (Main Processes):
  1.0 Authenticate User (login/register, issue JWT)
  2.0 Manage Tasks (create, update, delete, list)
  3.0 Update Checklist Progress (member ticks items)
  4.0 Generate Reports (Excel export)
  5.0 Display Dashboard (statistics and charts)

Data flows: login credentials → JWT; task JSON → database; checklist update
→ recalculated status → database; filter request → task list JSON.

3.6  Entity Relationship Diagram (ERD)

Entities: USER, TASK.

USER (userId PK, name, email, passwordHash, role, profileImageUrl)
TASK (taskId PK, title, description, priority, status, dueDate, progress,
      createdBy FK→USER, assignedTo FK→USER [multi-value array],
      todoChecklist [embedded: text, completed], attachments[])

Relationship: USER creates TASK (1:N). USER assigned to TASK (M:N via
assignedTo array in MongoDB document model).

3.7  Decision Table – Status from Checklist

+-------------+----------------+------------------+
| Condition   | Some completed | All completed    |
+-------------+----------------+------------------+
| Action      | In Progress    | Completed        |
+-------------+----------------+------------------+
| Else        | Pending (none completed)          |
+-------------+----------------+------------------+

3.8  Feasibility

Technical feasibility: MERN is well documented. Economic feasibility: open
source stack, Atlas free tier. Operational feasibility: browser-based, no
install for end users. Risks: Atlas IP whitelist, port 8000 conflicts — both
were faced and resolved during development.

4.4  Data Integrity Constraints

Email unique in User schema. Task title required. Enum validation on priority
and status. Member cannot call admin-only routes. Task access checks assignee
id even when assignedTo is populated from Mongoose.

4.5  API Design (REST)

POST /api/auth/register, POST /api/auth/login
GET/POST/PUT/DELETE /api/tasks/...
PUT /api/tasks/:id/todo — checklist update
GET /api/tasks/dashboard-data (admin)
GET /api/tasks/user-dashboard-data (member)
GET /api/reports/tasks, GET /api/reports/users

4.6  User Interface Design

Common layout: top bar, left sidebar with profile photo, white content card.
Colour coding: purple pending, cyan in progress, green completed. Task cards
show priority badge and due date. Forms use validation before submit. Toast
messages confirm save and delete actions.

                   CHAPTER 5 – IMPLEMENTATION
================================================================================

5.1  Project Folder Structure

TaskManager/backend — server.js, controllers, models, routes, middleware
TaskManager/frontend/Task-Manager — React source (src/pages, components)
TaskManager/scripts — database clear, docx generator
TaskManager/README.md — setup instructions

5.2  Backend Implementation

server.js connects MongoDB then listens on PORT. taskController.js filters
tasks: admin sees all; member uses assignedTo: { $in: [userId] }.
updateTaskChecklist counts completed items and sets status automatically.
isUserAssignedToTask compares ids when assignedTo contains populated objects.

5.3  Frontend Implementation

React Router paths for /admin/* and /user/*. PrivateRoute checks JWT role.
Admin: Dashboard, ManageTask, CreateTask, UpdateTask, ManageUsers.
Member: UserDashboard, MyTasks, ViewTaskDetails with live checklist API calls.

5.4  Security Implementation

JWT sent in Authorization header. Passwords hashed on register. Admin
registration requires ADMIN_INVITE_TOKEN match. Members blocked from other
users' tasks by server-side check on getTaskById.

Important source files are in the project folder. Below are representative

6.1  Task Schema (backend/models/Task.js)

Defines title, priority, status, dueDate, assignedTo array, embedded
todoChecklist sub-documents, and progress field. Mongoose timestamps record

6.2  Checklist and Status Logic (excerpt – taskController.js)

// When member updates checklist, server recalculates progress and status:
const completed = todoChecklist.filter((item) => item.completed).length;
const total = todoChecklist.length;
const progress = total ? Math.round((completed / total) * 100) : 0;
let status = "Pending";
if (completed > 0 && completed < total) status = "In Progress";
if (total > 0 && completed === total) status = "Completed";

This rule removes the need for members to pick status manually from a dropdown.

6.3  Assignee Authorization (excerpt – taskController.js)

const isUserAssignedToTask = (task, userId) => {
  return (task.assignedTo || []).some((entry) => {
    const assigneeId = entry?._id ? entry._id.toString() : entry.toString();
    return assigneeId === userId.toString();
  });
};

This fix was required because Mongoose populate returns objects, not plain ids.

6.4  React Route Guard (concept – PrivateRoute)

If localStorage token is missing or role does not match route prefix, user is
redirected to /login. Admin routes under /admin; member routes under /user.

6.5  Excel Export (reportController.js)

Uses ExcelJS to write columns: Task ID, Title, Description, Priority, Status,
Due Date, Assigned To names. Admin downloads file from Manage Tasks page.

================================================================================
              CHAPTER 9 – LIMITATIONS OF THE PROJECT
================================================================================

9.1  Technical Limitations

The system was tested with a small number of users and tasks. Very large
datasets may slow down chart rendering and list pages. There is no automated
test suite (Jest/Cypress) in the submitted version.

9.2  Functional Limitations

Attachments are URL links only; direct file upload for task documents is not
fully implemented. There is no email or SMS notification when a task is
assigned. Password reset and two-factor authentication are not included.
Real-time updates without page refresh use manual refetch, not WebSockets.

9.3  Deployment Limitations

The demo runs on localhost. Production deployment on HTTPS domain, backup
policy, and server monitoring were not part of this phase. MongoDB free tier
has storage and connection limits.

9.4  Security Limitations

JWT in localStorage is convenient for learning projects but has known XSS
risks; httpOnly cookies would be stronger for production. Rate limiting on
login API is not implemented.
